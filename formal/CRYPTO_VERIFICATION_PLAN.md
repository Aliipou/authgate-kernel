## 2. Correction: Fiat-Crypto is already in the dependency graph

`formal/lean4/FreedomKernel/Ed25519.lean:26-27` states:

> There is no HACL*/Fiat/EverCrypt code anywhere in the dependency graph.

**That is false.** `authgate-kernel/Cargo.lock:634` pins `fiat-crypto 0.2.9`,
and `Cargo.lock:477-489` shows `curve25519-dalek 4.1.3` depending on it
unconditionally.

The accurate statement is narrower and more useful: Fiat-Crypto's verified
field arithmetic is **compiled but not selected**. `curve25519-dalek` chooses
its arithmetic backend at build time, and with no `curve25519_dalek_backend`
cfg set it defaults to `simd`/`serial`, not `fiat`. So the verified code ships
in the binary's dependency tree and is never called.

This matters because it changes the cost of the first step from "adopt a new
cryptographic library" to "set a build flag".

## 3. Route A — select the Fiat-Crypto backend (cheap, partial)

```bash
RUSTFLAGS='--cfg curve25519_dalek_backend="fiat"' cargo build
```

`curve25519-dalek`'s `fiat_backend` integrates Rust generated by Fiat
Cryptography, whose primitive curve operations are extracted from Coq proofs of
arithmetic correctness.

**What this covers:** field arithmetic on GF(2²⁵⁵−19) — the modular
add/sub/mul/square/invert operations underneath every curve operation. This is
the layer where hand-written carry-propagation bugs historically live.

**What this does NOT cover, and must not be claimed:**

- Point decompression and encoding (RFC 8032 §5.1.3 canonical checks)
- Small-order / cofactor handling — precisely the `SmallOrder` hypothesis the
  axiom already carries, and the reason the TCB's use of non-strict `verify`
  is a live gap
- Scalar range checking (`S < ℓ`)
- The verification equation's assembly into `verify()`
- Constant-time behaviour of the surrounding code
- **Unforgeability.** See §6 — this is the important one.

So Route A shrinks the axiom's exposed surface. It does not discharge the
axiom, and a status table must not move on the strength of it alone.

**Cost:** one build flag, plus a benchmark to record the performance delta, plus
a CI job that builds both ways. Recommended immediately regardless of Route B.

## 4. Route B — `libcrux-ed25519` (the real answer, pre-release)

[`libcrux-ed25519`](https://crates.io/crates/libcrux-ed25519), from Cryspen, is
safe Rust compiled from verified C originating in the **HACL\*** project. The
underlying code is verified in **F\*** for memory safety, functional
correctness, and *secret independence* (resistance to some classes of timing
side channel). The workspace also exposes `hacl-rs`.

This is the lineage named in the commitment made to Chlipala, so this is the
route that honours it.

**What this covers that Route A does not:** the whole verification routine
rather than only the field arithmetic, plus a machine-checked
secret-independence property that speaks directly to gap 7 in
`Ed25519.lean` ("NOT constant-time execution", currently out of scope by
declaration rather than by evidence).

**Caveats to state plainly:**

- The crates are **pre-release, all versioned below 0.1**. Adopting one into a
  TCB is a judgement call, not a free win; version churn is expected.
- The verification is of the *extracted/compiled* artifact against its F\*
  specification. The Rust one links is downstream of that pipeline, and the
  pipeline itself (F\* → C → Rust) is part of what one is then trusting.
- Swapping libraries changes the concrete artifact named in the axiom's scope
  section, so `Ed25519.lean:17-27` must be rewritten in the same commit or the
  axiom will be documenting a dependency that is no longer there.

**Recommendation:** Route A now (it is a build flag and it is Chlipala's own
project), Route B as the tracked target, with the axiom rewritten to match
whichever is actually linked.

## 5. What "connect the proofs formally" requires

This is obligation 3, and it is the one with real design content. Today there
are two disconnected artifacts:

- a Lean axiom asserting EUF-CMA for an opaque `Verify`, and
- (prospectively) an F\*/Coq proof about a concrete implementation,

with **no formal relationship between them.** Swapping the library would silently
replace one informal trust assumption with another, and the Lean development
would not notice. "Connecting the proofs" means making the swap an
*instantiation* that Lean checks, rather than an edit that a human asserts.

### 5.1 Parameterise, don't axiomatise

Replace the free-standing axiom with an interface the kernel is proved against:

```lean
/-- The contract the kernel needs from *any* signature checker. -/
structure SignatureScheme where
  PubKey : Type
  Sig    : Type
  Verify : PubKey → Msg → Sig → Bool
  Signed : PubKey → Msg → Prop
  SmallOrder   : PubKey → Prop
  Compromised  : PubKey → Prop
  /-- The obligation an implementation must discharge. -/
  euf_cma : ∀ pk m s,
      ¬ SmallOrder pk → ¬ Compromised pk →
      Verify pk m s = true → Signed pk m
```

Every kernel theorem then takes `(S : SignatureScheme)` as a parameter. Two
instances:

- `ed25519Assumed` — `euf_cma := ed25519_euf_cma` (today's axiom). Honest, and
  the only instance currently available.
- `ed25519Verified` — `euf_cma := <theorem exported from the verified
  implementation>`. **Does not exist yet.** Its type is the precise statement of
  what a verified implementation would have to supply, which is itself the
  useful artifact: it turns "we will swap in HACL\*" from an intention into a
  proof obligation with a checkable type.

The payoff: the day `ed25519Verified` exists, the kernel proofs are re-checked
against it with no edits, and `#print axioms` on the top-level theorems stops
listing `ed25519_euf_cma`. That transition is machine-checked. That is the
formal connection.

### 5.2 `#print axioms` as the evidentiary standard

Every headline theorem carries its `#print axioms` output in the repository, as
`Ed25519.lean:118` already does. A claim's axiom footprint is then a fact a
reviewer reads off the build, not a sentence we wrote. This also permanently
closes the failure mode that produced the vacuous `sig_euf_cma ... : True`
axiom this file replaced.

### 5.3 The other two disconnections

Named for completeness, because "connect the proofs" applies to them equally and
neither is addressed by any crypto library:

- **TLA+ ↔ Lean.** `sig_valid` is an opaque `BOOLEAN` field in
  `authgate_v3.tla`, and `Verify` is an opaque function in Lean. Nothing relates
  them. The refinement obligation — that the TLA+ model's `sig_valid` is exactly
  `Verify pk m s` under the message-construction map — is unstated and unproved.
- **Lean ↔ Rust.** The code-to-spec step is admitted. Until it is discharged,
  the Lean development constrains a model of the kernel, not the kernel.

Both are instances of the axiom-to-code gap tracked in `ASSUMPTIONS.md`.

## 6. The limit: what no implementation proof can discharge

This is the part most likely to be got wrong in a status table, so it is stated
before anyone is tempted.

Verifying an Ed25519 implementation gives **functional correctness with respect
to RFC 8032** — the code computes the verification equation the standard
specifies. It does **not** give **EUF-CMA**. Unforgeability is a *computational
hardness* assumption about the underlying mathematics; it is established by
reduction (to discrete log, in the random-oracle model), not by proving that an
implementation matches its specification.

The current axiom `ed25519_euf_cma` conflates the two. It should be **split**:

| Component | Statement | Dischargeable? |
|---|---|---|
| **(a) Implementation correctness** | `Verify` computes exactly the RFC 8032 verification predicate | **Yes** — by Route A (partially) or Route B (substantially). This is the part Chlipala's advice targets |
| **(b) Cryptographic hardness** | An adversary without the private key cannot produce a message/signature pair satisfying that predicate | **No.** Irreducibly assumed. A verified implementation does not touch it |

After both routes land, the honest claim is therefore *not* "the signature
checker is verified". It is:

> The signature checker is verified to compute the RFC 8032 predicate. That the
> predicate is unforgeable remains a standard cryptographic assumption, stated
> as axiom (b), and no implementation proof will ever discharge it.

That claim is smaller than "verified crypto" and it is one we can actually
defend. Splitting the axiom is worth doing **before** either library change,
because it is the step that determines what the library change is allowed to
buy — and it costs nothing but care.

## 7. Ordered plan

1. **Split the axiom** into (a) implementation-correctness and (b)
   EUF-CMA-hardness. Pure Lean, no dependency change. Determines what everything
   downstream may claim. *(Blocked on: `lake build` currently failing for 5 of 6
   files — fix that first, or the refactor cannot be validated.)*
2. **Introduce `SignatureScheme`** and re-parameterise the kernel theorems;
   instantiate with `ed25519Assumed`. Record `#print axioms` for every headline
   theorem.
3. **Route A**: build with the Fiat backend, benchmark, add a CI job building
   both ways. Update `Ed25519.lean`'s scope section — including the false
   "no Fiat in the dependency graph" line corrected in §2.
4. **Fix the live gaps the axiom's hypotheses expose**, which are cheaper than
   any of the above and currently unaddressed: call `verify_strict` rather than
   `verify`, or check `is_weak()` at `CallGate::new`, so `¬ SmallOrder pk` stops
   being a hypothesis nothing discharges (`Ed25519.lean:88-92`). Add domain
   separation across the three signing grammars (gap 5) — currently the only
   thing preventing cross-protocol confusion is three message lengths happening
   to be pairwise distinct.
5. **Route B**: evaluate `libcrux-ed25519` against the pre-release risk; if
   adopted, write `ed25519Verified` and delete nothing else.
6. **Reply to Chlipala** with (1)–(4) done, stating the §6 split explicitly. The
   split is the substantive answer to "connect the proofs formally", and it is
   more interesting than the library swap.

Step 4 deserves emphasis: it is a real security improvement, it requires no
formal methods at all, and it is currently sitting behind three items of proof
engineering.
